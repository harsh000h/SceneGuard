# Publishing: GitHub, Play Store, and what this thing even is

Scope locked per the brief: **nudity/sexual content is skipped or blurred.
Violence, gore and abusive language are detected, kept, and at most marked or
muted — never cut.** That is now a code invariant (`SKIP_ELIGIBLE` in
`sceneguard/schema.py` and `extension/core.mjs`), tested on both sides:
19/19 Python, 16/16 JS. A config or a hand-edited manifest cannot break it.

---

## 1. Can you put this on GitHub as open source? — Yes

**No legal blocker on the code.** Publishing source is lawful. The things people
worry about are mostly not the real risks:

| Question | Answer |
|---|---|
| Is a list of timestamps ("adult scene at 01:23:14–01:25:02") copyrightable? | A timestamp is a fact, not an expression. Databases of facts are thin ice for a claim; you are not copying footage, dialogue or artwork. |
| Does publishing the *reader* (extension/CLI) make me liable for what others do with it? | You publish no decryption, no keys, no capture, no re-encode. Keep it that way and there's nothing to circumvent. |
| Will a studio send a letter anyway? | Possibly — ClearPlay existed for 25 years and still got litigated *around*. Your defensible position is "we seek, we never copy", so the letter has nothing to attach to. |

**License: use GPL-3.0-OR-LATER + CC0 for the data.**
- **GPL-3.0** for code: anyone who forks it must stay open, so nobody resells your work as a paid closed app. It also carries an anti-DRM clause you *want*: it refuses to grant patent/copyright licences that would enable circumvention, which reads well if a lawyer ever looks at your repo.
- **CC0 / ODbL** for the manifest data (`sceneguard/schema.py` sets `"license": "CC0-1.0"` already). You *want* the timestamp database copied and spread — data is the moat only if it's the biggest and most-trusted, and open data is how crowd contributions arrive.

**Five things to fix before the repo is public:**
1. **Name and trademark.** Do not call it "Netflix Filter". Repo name = your brand; mention platforms only descriptively ("works on Netflix"); no logos, no studio artwork, no screenshots showing a studio's key art in the README hero.
2. **LICENSE file + README "what this does not do"** section stating: no decryption, no capture, no download, no re-hosting, no copy.
3. **Delete the DRM-adjacent temptation.** If someone opens a PR adding `--record-and-analyze`, close it and link to §0 of `ANDROID.md`. Write that in `CONTRIBUTING.md`, or you'll have the fight twice.
4. **Selftest fixture is fine to commit** (`extension/fixtures/synthetic.mp4` is generated by code, 22 KB, no third-party content). Add `LICENSE-CC0` for it if you like.
5. **Privacy:** the extension talks only to your own API with `credentials: "omit"` and stores prefs in `chrome.storage`. Keep it that way — that's the claim that survives scrutiny ("we never see what you watch"), and it's true today.

GitHub is also, in practice, the *distribution channel* for this category — Skipit is open-source and installed from the Chrome Web Store. That combo is the model to copy.

## 2. Can you upload an app to the Play Store? — Not this one

Two independent blockers, and neither is about DRM:

**a) A browser extension can never go on the Play Store at all.** Chrome
extensions ship via the Chrome Web Store (already free, no review gate as strict,
no 12-tester requirement). Play Store only accepts APKs/AABs running on Android.

**b) An Android app that wraps Netflix/Prime/JioHotstar in a WebView gets rejected,**
on two of Google's own rules:
- **Policy 4.3 minimum functionality:** *"apps that simply load a website URL,
  redirect users to an external site, or have no dynamic features will be rejected"*,
  and wrappers of a site **the developer does not own or manage** are treated as
  spam/trademark violations. Our TV-box idea (ANDROID.md §1) is exactly that shape.
- **Device & Network Abuse / content-protection:** an app whose purpose is altering
  the behaviour of another app's protected playback invites removal even when it only
  seeks. Google has removed far milder things.

Plus practicals: new personal developer accounts must run **12 testers for 14 days**
of closed testing before production, and India's IT Rules age-gating obligations
apply to *publishers* — you'd want a clear "this is a viewer-side control, we publish
no content" statement.

### What *would* pass Play review today
Ship component **A** only: **a personal media filter for files the user owns.**

| Feature | Play-safe? |
|---|---|
| Import a `.sceneguard.json` manifest, play local DRM-free video, skip/blur/mute on it | ✅ clean — no other app involved |
| Scan the user's own video files to draft timestamps, human confirms | ✅ with an on-screen consent line: "we analyse only files you select, on your device" |
| Community timestamp browser for Indian titles (data, not video) | ✅ as long as no footage is shown — metadata + your own descriptions |
| Any WebView of a streaming site, any "works with Netflix" button, any capture | ❌ don't |

**So the honest split:** open-source + Chrome Web Store = the streaming use case.
Play Store = the local-files / FamilyWatch-rating app. Distribute the TV-box build
by **sideload / own website**, never through Play, and say so in the store listing
so you're not the app that gets pulled in month three.

## 3. Is what we made a tool or an app? — It's a tool, and the app is the shell

Both words matter because they decide distribution, price and who maintains it.

| Artefact in this repo | Category | Who uses it | Distribution |
|---|---|---|---|
| `sceneguard/` — `analyze`, `mark`, `rate` | **CLI tool** | you / curation volunteers | GitHub, `pip install` |
| `extension/` — MV3 content script + `core.mjs` | **browser extension** | your parents, on the laptop | Chrome Web Store |
| proposed A — Media3 player + manifest import | **Android app** | the family offline library | Play Store |
| proposed B — Android-TV WebView shell | **device app** | living room | sideload only |
| `sceneguard/schema.py` manifest format | **open data spec** | *every* client above | the repo's real product |

The important line: **the product is the timestamp data plus the manifest spec. The
app is a shell that reads it.** Tools are maintained by whoever runs them; apps are
maintained by you for everyone. That's why VidAngel/ClearPlay/Skipit all look like
thin clients over a database — and why you should open the format and the readers
(GitHub, GPL) and keep the curated Indian catalogue as the thing worth subscribing to.

## 4. Binaries: "add APK versions for mobile and desktop"

**Terminology, because it decides what is even possible:** an **APK is Android-only**.
"Desktop APK" does not exist; the desktop equivalents are `.exe` / `.dmg` / `.AppImage`.
And our desktop capability is a Chrome **extension**, which is neither an APK nor an
`.exe` - it is `chrome://extensions`, installed once per browser profile.

What the repo now ships:

| Requested | Shipped as | Realistic? |
|---|---|---|
| mobile APK | `android/` Gradle project + `android-apk.yml` → debug APK + release AAB on tag | ✅ buildable; **not yet run on a device** |
| "desktop APK" | `desktop/app.py` + `desktop-binaries.yml` → Win/macOS/Linux via PyInstaller | ✅ works, local files only |
| desktop *streaming* | `extension/` unpacked folder | ✅ the correct answer, no installer needed |
| Play Store listing | only the local-file Android app qualifies | ⚠️ §2 above |

Why binaries are produced by CI and not committed: a committed `.apk`/`.exe` is
un-auditable (every "open source" project that ships one is trusting the maintainer's
laptop), the Android SDK is not present in this environment, and GitHub release assets
for unsigned builds trigger Play Protect's *"app isn't verified"* warning on install —
so a committed APK would be a *worse* experience than a tagged CI build. Tag `v0.1.0`
after pushing and the artifacts appear on the release page automatically.

## 5. Publishing this repo: the credential rule, then the commands

**Do not send me your GitHub password or your username+PAT in chat.** Treat a PAT like a
password: anything pasted into a chat is retained in the conversation, and this sandbox
snapshot-persists files — a token written into the workspace would outlive the session.
Also note GitHub removed password authentication for git over HTTPS years ago, so a raw
account password cannot push anyway.

### Option A — you create and push (recommended, ~2 minutes, nothing shared)

```bash
cd sceneguard
# repo already committed here (branch main, 51 files). Set your handle first:
grep -rl "REPLACE_ME" . | xargs sed -i "s/REPLACE_ME/<your-github-handle>/g"
git remote add origin https://github.com/<your-github-handle>/sceneguard.git
git push -u origin main
git tag v0.1.0 && git push origin v0.1.0     # CI then builds the APK + desktop binaries
```
Create the repo on github.com first as **empty** (no README, no licence — ours are in
the tree, and GitHub's auto-generated ones collide with them).

### Option B — scoped token, short-lived (only if you want me to run the push)

1. github.com → Settings → Developer settings → **Fine-grained tokens** → Generate.
2. Repository access: **Only select repositories** → the one repo. Permissions:
   **Contents: Read and write** only. Expiration: **7 days** (minimum).
3. Hand that token over *only* if you accept that it can read and write that repo, then
   **revoke it the moment the push is done** (Settings → Developer settings → tokens).
4. Never a classic `repo`-scoped token, never one without an expiry, never your password.

I can prepare and commit everything (done) and run the two `git push` lines, but I will
not store a token in the workspace, and I will not use it for anything beyond that push.

### After the first push, do these four things

| # | Action | Why it is not optional |
|---|---|---|
| 1 | Replace `REPLACE_ME` in `README.md` badges + `pyproject.toml` | dead badges and a broken repo URL on the first thing every visitor reads |
| 2 | Settings → Security policy → point at `SECURITY.md`; enable **Private vulnerability reporting** | parental-control software without a disclosure path looks careless or worse |
| 3 | Description + topics: `parental-control`, `content-filter`, `chrome-extension`, `netflix-alternative-parental`, `india`, `ott` | discovery in this niche is almost entirely topical search |
| 4 | Turn on GitHub Releases for the `v0.1.0` artifacts | that is the whole distribution story: no binaries in git, reproducible builds from a tag |

### What NOT to put in the repo, ever
- Any `.apk`/`.exe` you built by hand (un-auditable, and Play Protect flags the debug one).
- Screenshots showing a platform's key art, or a logo in the repo name/avatar ("Netflix
  Filter" is a trademark problem before it is a discoverability one).
- The scraped/streaming video of anything. Timestamps and your own prose only.
- A `/server/.env`, admin token, or API key. `check-repo.py` scans for credential-shaped
  strings (PATs, JWTs, AWS keys, private-key headers) and fails the run on a match.
